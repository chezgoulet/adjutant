## #30 — retired plugin pools are never closed

Every hot reload pushes the outgoing `LoadedPlugin`s into `retired` and nothing closes their
`PgPool`s. Two connections per plugin, leaked per reload, against Postgres's default 100 —
about fifteen reloads and the server cannot open new connections at all, including its own
core pool.

- Close a plugin's pool when the plugin is retired (uninstall and `replace_all`). `PgPool::close()`
  drains gracefully: existing checked-out connections finish, new ones are refused, so an
  in-flight request holding an `Arc` clone completes.
- **Keep the `.so` mapped** — retiring the *library* is deliberate and must not change. Only
  the pool closes.
- If you need a grace period rather than an immediate close, say why in the code and make the
  bound explicit; do not leave the pool to live forever.

**Probe (this is the acceptance criterion):** reload N times (say 10) and assert the count of
`adjutant_plugin_*` connections in `pg_stat_activity` stays constant. `retired_count()` counts
libraries, not connections — that is why this went unnoticed. State in the PR what the probe
measures and paste its output.

## #31 — the operator-facing half

1. **Refuse to boot on a superuser connection** unless `ADJUTANT_ALLOW_SUPERUSER=true` is set
   explicitly. The message names the reason (a plugin escape became total compromise while the
   role was a superuser) and the opt-out.
   - **CI note:** the workflow's Postgres user *is* a superuser, so set the opt-out explicitly in
     `ci.yml` with a comment saying why (throwaway database). Cover the refusal itself with a
     test rather than relying on CI to exercise it.
2. **`isolated` on the admin surface** — `PluginInfo.isolated` (true, or the plugin is absent)
   and in the `list_plugins` payload, so an operator can see isolation is active instead of
   inferring it from a boot log line.
3. **A dedicated `adjutant_app` role** in `docker-compose.yml` and `docs/deployment.md`: no
   `SUPERUSER`, no `CREATEROLE`, owns nothing, holds the plugin roles, plus the `core.*`
   privileges the core services need. Verify the superuser check passes with it and that the
   server boots end to end on the compose path.
4. **The quick start must include the bootstrap.** `bootstrap-isolation` is a one-off, it needs
   the plugin directory present (it iterates what is on disk), and it must be re-run when a
   plugin is added. Say all three in `docs/deployment.md`, next to the `docker compose up -d`
   line, and make the failure mode (unbootstrapped plugin → `NotBootstrapped`, exit 1) a
   documented, expected state rather than a mystery.
